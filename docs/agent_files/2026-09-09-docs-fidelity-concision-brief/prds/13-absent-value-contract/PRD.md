# PRD 13 — Absent-Value Contract

Parent brief: `docs/agent_files/2026-09-09-docs-fidelity-concision-brief/brainstorm.v1.md` (approved; not re-litigated here).
Branch: `docs/fidelity-concision-brief`.
Depends on: 01 (schema/nullability precedent — `WarningSign.urgency`), 04 (the "Not stated in your note." sentinel and the content-richness floor), 05 (the reviewer/corrector op vocabulary and the corrector-diff check), 08 (both render paths, `nextSteps.ts`).
Depended on by: nothing directly, but shares two files with 14 (merge-provenance) — see §4.7 for the stated interface seam.

## 1. Problem

"The note didn't say" is currently represented as a piece of rendered English text baked directly into the data layer. `Medication.why`, `Test.why`, `Procedure.why`, and `OtherInstruction.why` (`backend/models/care_plan/care_plan.py:34,49,59,68`) are all `str = ""`, and when the assembly LLM has no fact to ground a reason in, `assemble_and_render.txt` instructs it to write the literal sentence `"Not stated in your note."` into the field (`backend/care_plan/prompts/assemble_and_render.txt:28`). The reviewer's `not_stated` correction op and the corrector's own instruction (`backend/care_plan/prompts/correct.txt:10`) repeat the same literal string as the thing to write. There is no typed way to distinguish "the model deliberately marked this absent" from "the model wrote a nine-character string that happens to start with a capital N" — absence is encoded as content, not as a value.

Verified by repo-wide grep, every production location that currently names this sentence:

```
backend/care_plan/prompts/assemble_and_render.txt:28: ... set why to exactly this sentence: "Not stated in your note." ...
backend/care_plan/prompts/correct.txt:10: For a "not_stated" entry: set that exact field to precisely this text and nothing else: "Not stated in your note."
backend/care_plan/pipeline.py:373: (docstring) "Not stated in your note." (25 chars) always clears the length rule on its own, so the sentinel is never flagged here.
```

A fourth, related location doesn't repeat the literal string but hard-codes the *behavior* the string exists to produce: `backend/care_plan/prompts/review.txt:12` — `"not_stated": ... Do not set a value -- the fixed sentence is inserted downstream.` The literal string also appears in nine backend test assertions across four test files (`test_pipeline_assembly.py`, `test_pipeline_correct.py`, `test_pipeline_prompts.py`, `test_pipeline_review.py` — full list in §7). It does **not** appear anywhere in `frontend/` today — a repo-wide grep for `"Not stated"` under `frontend/src` returns zero hits, confirming the string is currently synthesized entirely on the backend and shipped to the frontend as ordinary `why` text indistinguishable from any other sentence.

This is exactly the same class of problem PRD 01 already solved once, one field over: `WarningSign.urgency` used to default to `"monitor"` — an affirmative clinical claim the model never made — and PRD 01 made it `Literal[...] | None` with no default instead, an in-schema precedent for "a default is an affirmative claim the model never made" (PRD 01 §4.1). `why` has the identical defect in a different shape: instead of a fabricated default *value*, it has a fabricated default *string of prose*, generated by prompt instruction rather than by a Python default, but functionally the same category of problem — the schema cannot distinguish "the note said nothing" from "the model wrote nine words." Making `why: str | None` closes that gap the same way `urgency: ... | None` already did, and does so without changing what the patient sees: the reader still gets exactly the sentence "Not stated in your note." in exactly the same place — this PRD moves *where that string lives* (from three backend prompt/pipeline locations into one frontend render-layer constant), not what the reader reads.

The honest counter-argument, recorded rather than argued away: there is no second consumer of `why` today. No eval harness reads it, no translation path reads it, nothing downstream of the frontend distinguishes a real reason from a placeholder programmatically. The case for this PRD is not "a consumer needs this" — none exists yet — but internal consistency with the `urgency` precedent already in the schema, and the concrete win of deleting a hand-typed English sentence from three backend locations that must otherwise be kept byte-for-byte identical by hand forever (a maintenance hazard `urgency`'s nullability doesn't share, since a `Literal` enum can't drift the way three independently-edited copies of a 26-character string can).

## 2. Goals

- `why: str | None = None` on `Medication`, `Test`, `Procedure`, `OtherInstruction` (`backend/models/care_plan/care_plan.py`), with `""` normalized to `None` rather than left as a third legal state.
- Delete the literal sentence `"Not stated in your note."` from `assemble_and_render.txt` and `correct.txt`; both now instruct `null` instead.
- Establish, and record the reasoning for, exactly one place downstream that renders `null` back into the patient-facing sentence — the frontend, once, not the backend.
- Confirm (not merely assume) that PRD 05's `_sanitize_review_result`/`_WHY_PATH_RE` and the corrector-diff check (`_verify_correction_diff`/`_PII_ELIGIBLE_FIELDS`) tolerate `why` being `None` on either side of a correction, and specify any code change actually required (§4.3's answer: none to the matching/diff logic itself, by walked-through construction).
- Settle whether the reviewer's `not_stated` op should collapse into `remove` or `correct` now that its target is a value rather than a sentence, with a definitive answer either way (§4.3).
- Update `frontend/src/types/carePlan.ts` and audit every `.why` read site in the frontend for a truthiness assumption that would behave differently once `""` can no longer appear on the wire.
- Confirm PRD 04's content-richness floor (`_log_thin_fields`) does not misbehave — crash, false-flag, or silently swallow — on a `None` `why`.
- State the interface assumptions at the seam shared with PRD 14 (merge-provenance), which edits the same two files (`care_plan.py`, `assemble_and_render.txt`) for an unrelated field.

## 3. Non-Goals

- No change to `WarningSign.urgency`, `DiagnosisDetail.severity`, or any other nullable field — this PRD's only schema edit is the four `why` fields.
- No renaming of the `"not_stated"` correction op. §4.3 keeps the name (it still names the reviewer's *judgment* — "the plan asserts a reason its fact doesn't support" — even though what the corrector now *does* about it changes from writing a sentence to writing `null`).
- No new fifth pipeline call, no eval-harness or translation-path consumer built for `why` being typed — those don't exist and building for them now would be exactly the speculative generality §1 explicitly declines to argue from.
- No change to `Medication.change`, `Diagnosis`, or any other field's fold/nullability decided by 01/08 — out of scope.
- No change to PRD 14's territory: this PRD does not add, name, or design a `merged: bool` field. §4.7 states only the shared-file interface assumptions PRD 14 needs to know about.
- No change to `frontend/src/components/CarePlanView.tsx` or `frontend/src/utils/buildPdfHtml.ts` source code. §4.5/§4.6 show this is not an oversight: both files already render `why` exclusively through `NextStepRow.why`, which is entirely populated by `frontend/src/utils/nextSteps.ts`'s `buildNextStepsRows` — the one function both files call. Fixing the fallback at that single choke point means neither renderer needs to know `why` can be absent at all.
- No versioning, no migration, no dual-schema support (global constraint) — `Constants.Schema.CARE_PLAN_VERSION` is untouched.

## 4. Architecture Decisions

### 4.1 `backend/models/care_plan/care_plan.py` — `why` becomes nullable, `""` is not a legal third state

Old → new, all four models (`care_plan.py:34,49,59,68`):

| Model | Field | Old | New |
|---|---|---|---|
| `Medication` | `why` | `str = ""` | `str \| None = None` |
| `Test` | `why` | `str = ""` | `str \| None = None` |
| `Procedure` | `why` | `str = ""` | `str \| None = None` |
| `OtherInstruction` | `why` | `str = ""` | `str \| None = None` |

**Decision: `""` is not legal input. It is normalized to `None`, not preserved as a third state.** The task brief for this PRD is explicit that a three-state field (`None`, `""`, real text) would be worse than the current two-state one (`""`, real text) — so the fix must actually collapse to two states, not add a third. Unlike `WarningSign.urgency` (a `Literal`, where `""` was never constructible in the first place), `why` is a bare `str`, so `""` remains syntactically valid unless something rejects or rewrites it. This codebase has no existing validator idiom for a field like this — grepped `care_plan.py`/`base.py` for `field_validator`/`validator`: zero hits; `CarePlan.note: str | None = None` (`care_plan.py:117`, untouched by this PRD) is the only other `str | None` field in the schema, and it has no normalization guard either (a pre-existing, narrower version of the same gap, out of scope here — `note` is populated from upload metadata, not LLM prose, so it has never been observed to carry a placeholder sentence).

The fix is a `mode="before"` field validator, one function shared across the four classes rather than four independent inline lambdas:

```python
def _blank_str_to_none(v: object) -> object:
    """Normalize an empty string to None so a field validated by this
    helper is always exactly one of {None, non-empty text} -- never a
    third, indistinguishable "" state (PRD 13 S4.1). `object`, not
    `str | None`: Pydantic calls a mode="before" validator with
    whatever raw value was actually given, before type coercion runs --
    a non-str value here is returned unchanged and Pydantic's own type
    check raises on it immediately afterward, exactly as it would have
    without this validator in the chain."""
    return (v or None) if isinstance(v, str) else v
```

Wired into each of the four classes identically:

```python
class Medication(JsonModel):
    title: str = ""
    plain_name: str = ""
    why: str | None = None
    dosage: str = ""
    frequency: str = ""
    timing: str = ""
    duration: str = ""
    instructions: str = ""
    side_effects_to_watch: str = ""
    change: str = ""
    status: Literal["to_do", "done"]
    source_fact_ids: list[int] = Field(default_factory=list)

    @field_validator("why", mode="before")
    @classmethod
    def _normalize_why(cls, v):
        return _blank_str_to_none(v)
```

(Same three-line `_normalize_why` classmethod added to `Test`, `Procedure`, `OtherInstruction`, right after each class's own `why` field line.) Requires adding `field_validator` to the existing `from pydantic import Field` import at the top of the file.

*Alternative considered and rejected*: normalize `""` → `None` as a one-off guard inside `_verify_assembly` (`pipeline.py`) instead of a model-level validator. Rejected because `_verify_assembly` only runs after `assemble_and_render`'s LLM call — it would leave `correct()`'s `CarePlan.model_validate(raw)` (`pipeline.py:821`) and every direct test/fixture construction of these four models unguarded, so `""` could still enter via the corrector's output or via a hand-built fixture. A `mode="before"` validator on the field itself fires on every construction path uniformly — `assemble_and_render`, `correct`, and any test — with no risk of a second, un-normalized entry point being added later.

**Why keep the default (`= None`), rather than making `why` required-with-no-default like `urgency`?** `urgency` (PRD 01 §4.1) is required-but-nullable specifically because it is *always extracted* for every warning sign the model chooses to include — the field asks "what's your judgement," and "I have none" is itself a judgement that must be recorded, never silently skipped. `why` is different: it is one of many optional descriptive fields on an item (`dosage`, `frequency`, `timing`, `instructions`, `side_effects_to_watch` are all `str = ""` too), and PRD 01 already established the precedent that this codebase's ordinary informational string fields default rather than require (see PRD 01 §4.1's `Medication.change` fold rationale, which makes exactly this argument for why `change` stays a defaulted `str` and not an `Optional[str] = None` with no default). Keeping `= None` as the default is that same idiom applied one type wider: `why` behaves like every sibling field on the same model, just with a two-value instead of one-value empty state.

### 4.3 Pipeline guards — what actually needs to change (`backend/care_plan/pipeline.py`)

This is the subtlest part of the PRD; each of the four guards is walked through against the real code rather than assumed safe.

**`_log_thin_fields` (`pipeline.py:367-391`) — no logic change.** The relevant line:

```python
value = getattr(item, attr, "")
if value and not _is_informative_quote(value):
```

`getattr(item, attr, "")`'s `""` default never actually fires — `why` is a declared field, always present on the instance, so `getattr` returns the field's real value (`None` or text), never the fallback. `if value and ...` treats `None` exactly as it already treated `""`: both are falsy, both short-circuit before `_is_informative_quote` is ever invoked. **Nothing breaks, nothing needs to change beyond the docstring fix in §4.2** — this was already true before this PRD; the field-richness floor was never actually exercised by an empty string either, for the identical reason.

**`_verify_assembly` (`pipeline.py:394-446`) — no logic change.** None of its three guards (`questions` truncation, `summary_fact_ids` pruning, `source_fact_ids` pruning/item-dropping) reads `why` at all. `_log_thin_fields(model)` is the only place in this function that touches `why`, covered above.

**`_sanitize_review_result` / `_WHY_PATH_RE` (`pipeline.py:449,471-505`) — no logic change.** `_WHY_PATH_RE = re.compile(r"^(medications|tests|procedures|other)\[\d+\]\.why$")` matches on the **path string**, never on the field's current or target value — whether `why` is presently `None`, `""` (pre-this-PRD), or real text is invisible to this regex, and remains so. `_sanitize_review_result`'s other checks are also value-shape-agnostic for `not_stated`: it drops a `not_stated` only when the *path* fails `_WHY_PATH_RE.match`, never based on what `why` currently holds. **No change required.**

One adjacent check *does* interact with `why`'s value, but for the `"correct"` op, not `"not_stated"`:

```python
if c.op == "correct" and not c.value:
    logger.warning("review: dropping correct with no value: %r", c.path)
    continue
```

This is why `"not_stated"` cannot collapse into `"correct"` — see below.

**Does `"not_stated"` collapse into `"remove"` or `"correct"` now that its effect is "set to null" rather than "write a sentence"? No — for two independent structural reasons, not a style preference:**

1. **It cannot become `"remove"`.** `remove` deletes a whole array item (or, for the one hard-coded exception, sets `summary` to `""` — `correct.txt:12`). `_split_array_path` (`pipeline.py:544-565`), which every `remove` correction is converted through by the diff check, raises `SimplifyError` if the correction's path doesn't end in an `[N]` index:
   ```python
   m = _PATH_SEGMENT_RE.fullmatch(last)
   if not m or m.group(3) is None:
       raise SimplifyError(ErrorCode.PIPELINE_VALIDATION_FAILED,
           detail=f"remove correction does not address an array item: {path!r}")
   ```
   `medications[0].why` has no trailing `[N]` — it names a scalar field inside an item, not the item itself. Retargeting `not_stated` as `remove` would either delete the whole medication (wrong — the medication is still real, only its stated reason is unsupported) or crash `_split_array_path` outright. `remove` and `not_stated` operate at different granularities by design; nothing about `why` going nullable changes that.

2. **It cannot become `"correct"` with `value=null`.** `Correction.value: str | None = None` (`models/review.py:18`) already uses `None` as the sentinel for *"no value was supplied for this correction"* — that's exactly what `_sanitize_review_result`'s `if c.op == "correct" and not c.value: continue` guards against (a malformed `correct` the reviewer emitted with nothing to correct *to*). If `"correct"` were repurposed to also mean "set the target to null" when `value=None`, every legitimate null-target correction would be silently dropped by that exact guard — the two meanings of `value=None` ("missing" vs. "the real target is null") are indistinguishable on the wire without adding a second field (e.g. a `has_value: bool`) to `Correction` just to disambiguate them. That is strictly more machinery than keeping `not_stated` as the three-op vocabulary's dedicated "clear this field" verb, for a Correction model this codebase does not otherwise need to touch.

**Decision: `not_stated` stays a distinct third op, unrenamed. Only its effect changes** — the corrector writes `null` where it used to write a sentence (§4.2). The reviewer's *reason* for emitting the op is unchanged ("the plan asserts a reason its fact doesn't support"), so the name is still accurate to the judgment it records, even though the mechanical result downstream is now "field is null" instead of "field holds this exact string."

**`_verify_correction_diff` / `_diff_item` / `_PII_ELIGIBLE_FIELDS` (`pipeline.py:521-632`) — no logic change. This is the check the task brief specifically flags as the subtle one; walked through against the actual code below rather than assumed.**

The relevant branch, at a scalar leaf where `before_v != after_v`:

```python
if before_v == after_v:
    return
if path in named:
    return
field_name = path.rsplit(".", 1)[-1].split("[", 1)[0]
if isinstance(before_v, str) and isinstance(after_v, str) and \
   field_name in _PII_ELIGIBLE_FIELDS and _looks_like_pii_substitution(before_v, after_v):
    return
raise SimplifyError(ErrorCode.PIPELINE_VALIDATION_FAILED,
    detail=f"corrector changed unnamed, non-PII field: {path}")
```

Every transition a nullable `why` can produce, walked through:

| `before_v` | `after_v` | Named? | Outcome | Why |
|---|---|---|---|---|
| `None` | `None` | either | pass | `before_v == after_v` is `True` on the first line — returns immediately, regardless of naming. |
| `"real text"` | `None` | named (`not_stated`/`correct`) | pass | Not equal → falls to `path in named` → `True` → returns. Type mismatch (`str` vs `None`) never reaches the PII branch, which doesn't matter because the named-path check already passed. |
| `None` | `"real text"` | named (`correct`) | pass | Same as above, reversed. This is the exact case the task brief calls out — a `None → "text"` transition on a **named** path passes cleanly, because `_diff_item`'s named-path check is type-agnostic: it never inspects `isinstance` before deciding a named change is allowed. |
| `"real text"` | `None` | **not** named | **raises** | Not equal, not named. `isinstance(after_v, str)` is `False` (it's `None`), so the PII-substitution branch is skipped entirely — falls straight to the final `raise`. Correctly rejects an uninstructed silent field-clear. |
| `None` | `"real text"` | **not** named | **raises** | Same reasoning, reversed: `isinstance(before_v, str)` is `False`, PII branch skipped, raises. Correctly rejects the corrector inventing a reason out of nothing. |
| `"text A"` | `"text B"` (small edit) | not named, `why` eligible | pass (PII sweep) | Unchanged from today — both sides are `str`, so the existing PII-substitution path is reachable exactly as before. A `None` on either side is what newly *disables* that path (case above), never something that newly enables it. |

No branch of `_diff_item` needs a new `isinstance(..., type(None))` check, a new named-set entry, or a new `_PII_ELIGIBLE_FIELDS` carve-out. The function was already written type-agnostically at its equality/naming checks (`before_v == after_v` and `path in named` both work on any Python value) and only becomes type-*specific* at the PII branch, which is the one place a `None` correctly and automatically opts out simply by failing `isinstance(..., str)` — exactly the behavior wanted (a field with nothing in it has no name to swap). **Confirmed by this walkthrough, not assumed: `_verify_correction_diff`, `_diff_item`, `_looks_like_pii_substitution`, and `_PII_ELIGIBLE_FIELDS` require zero code changes.** `why` staying in `_PII_ELIGIBLE_FIELDS` (`pipeline.py:525`) is unaffected and still correct — the PII sweep still needs to be able to swap a name embedded in a real `why` sentence; it simply can no longer accidentally fire when one side is `None`, which is strictly safer than before, not a regression.

### 4.4 `frontend/src/types/carePlan.ts` — `why` becomes nullable, stays optional

Old (`Medication`/`Test`/`Procedure`/`OtherInstruction`, four identical `why?: string;` lines):
```typescript
why?: string;
```

New, all four:
```typescript
why?: string | null;
```

**Decision: keep the `?` (optional key), do not follow `WarningSign.urgency`'s "required key" precedent here.** This is a deliberate deviation from `urgency`'s pattern, made after auditing the actual cost of matching it exactly. Grepped every object literal in the frontend typed as `Medication`, `Test`, `Procedure`, or `OtherInstruction` (the only two files in the whole frontend that construct these types as literals — confirmed by `grep -rln ": Medication\b\|: Test\b\|: Procedure\b\|: OtherInstruction\b" frontend/src`, which returns exactly `frontend/src/types/carePlan.ts` itself and `frontend/src/tests/utils/nextSteps.test.ts`; `CarePlanView.test.tsx` and `buildPdfHtml.test.ts` construct them structurally via `SimplifiedCarePlan`/`Partial<SimplifiedCarePlan>` object literals, same effect):

- `frontend/src/tests/components/CarePlanView.test.tsx`: 10 medication/test/procedure/other object literals across the file (lines 15-18, 50-53, 64-67, 105, 115) omit `why` entirely.
- `frontend/src/tests/utils/buildPdfHtml.test.ts`: 8 more (lines 26, 28, 29, 30, 79-82, 104, 113).

Making `why` a required key would force `why: null,` (or a real string) onto all 18 of these pre-existing, PRD-08-authored literals purely to satisfy the compiler, for zero functional gain: unlike `urgency` (where PRD 08 built an exhaustive ternary that benefits from the compiler knowing the key is always there), nothing downstream branches on "is the `why` key present" versus "is `why`'s value falsy" — §4.5's `resolveWhy` treats a missing key and an explicit `null` identically by design. Keeping `?: string | null` costs nothing at runtime (Pydantic always emits the key on the wire either way; TypeScript's `?` is a compile-time-only convenience for object-literal authors, not a claim about the wire shape) and avoids ~18 mechanical, unrelated-to-this-PRD test edits. `urgency`'s required-key choice bought something concrete; a required `why` here would not.

### 4.5 `frontend/src/utils/nextSteps.ts` — the one place the fallback lives

**Verified this is the only place it needs to live.** Repo-wide grep for `.why` across `frontend/src` (excluding `node_modules`) returns exactly three call sites: the four `why: m.why` / `t.why` / `p.why` / `o.why` reads inside `buildNextStepsRows` itself, `CarePlanView.tsx:210`'s `row.why && ...`, and `buildPdfHtml.ts:68`'s `row.why ? ... : ''`. Both renderer sites read `NextStepRow.why` — a value already fully resolved by `buildNextStepsRows` before either renderer ever sees it. There is no fourth site, no per-section pre-merge medications/tests/procedures/other card left over from before PRD 08's eight-card collapse, and no direct read of `Medication.why`/`Test.why`/etc. anywhere outside this one function. This means the fallback needs exactly one implementation, in exactly one function, and — unlike a naive reading of "call it from both paths" — **neither renderer file needs to call anything new at all**, because both already call the one function that will apply it.

New exported constant and helper:

```typescript
export const WHY_NOT_STATED = 'Not stated in your note.';

// Single point through which BOTH CarePlanView.tsx and buildPdfHtml.ts see
// "why" -- neither reads Medication/Test/Procedure/OtherInstruction.why
// directly (verified: repo-wide grep for `.why` under frontend/src finds
// no other read site). A falsy check, not `== null`, so a stray "" that
// somehow reaches this function (it shouldn't -- the backend validator in
// S4.1 normalizes "" to None before this ever leaves the API) still gets
// the same fallback rather than rendering a blank "Why:" line, which is
// exactly the silent-omission failure mode this whole PRD exists to close.
function resolveWhy(why: string | null | undefined): string {
  return why || WHY_NOT_STATED;
}
```

Wired into the four (of five) row-builders that have a `why` field (`follow_up` has none — unchanged):

```typescript
export function buildNextStepsRows(carePlan: CarePlanContent): NextStepRow[] {
  const withTitle = (t: { plain_name?: string; title: string }) =>
    t.plain_name ? `${t.plain_name} (${t.title})` : t.title;

  const rows: NextStepRow[] = [
    ...(carePlan.medications ?? []).map((m): NextStepRow => ({
      type: 'medication', status: m.status, title: withTitle(m), why: resolveWhy(m.why),
      detail: joinDetail(m.dosage, m.frequency, m.timing, m.duration),
      change: m.change,
    })),
    ...(carePlan.tests ?? []).map((t): NextStepRow => ({
      type: 'test', status: t.status, title: withTitle(t), why: resolveWhy(t.why),
      detail: joinDetail(t.description, t.preparation),
    })),
    ...(carePlan.procedures ?? []).map((p): NextStepRow => ({
      type: 'procedure', status: p.status, title: withTitle(p), why: resolveWhy(p.why),
      detail: joinDetail(p.what_to_expect, p.timeframe),
    })),
    ...(carePlan.follow_up ?? []).map((f): NextStepRow => ({
      type: 'follow_up', status: f.status, title: f.description,
      detail: joinDetail(f.time_frame),
    })),
    ...(carePlan.other ?? []).map((o): NextStepRow => ({
      type: 'other', status: o.status, title: o.title, why: resolveWhy(o.why), steps: o.steps,
      detail: joinDetail(o.description, o.frequency, o.duration),
    })),
  ];
  // ... sort unchanged ...
}
```

The only lines that change from the current file are the four `why: m.why` → `why: resolveWhy(m.why)` (and `t.`/`p.`/`o.` equivalents). `NextStepRow.why`'s own type (`why?: string;`) is unchanged — `resolveWhy` always returns a non-empty string for the four types that call it, so the field is *effectively* always populated for `medication`/`test`/`procedure`/`other` rows and remains legitimately `undefined` only for `follow_up` rows, exactly as today.

### 4.6 `CarePlanView.tsx` / `buildPdfHtml.ts` — confirmed zero code changes

Both files' existing render code is already correct for the new contract, unmodified:

- `CarePlanView.tsx:210`: `{row.why && <p ...>Why: {withTerms(row.why)}</p>}` — `row.why` is now always a non-empty string for a row that has one at all (via `resolveWhy`), so this guard still does exactly what it did before: render the line when there's a `why` to show, skip it for `follow_up` rows where `row.why` is `undefined`.
- `buildPdfHtml.ts:68`: `${row.why ? ... : ''}` — identical reasoning.

This is the concrete answer to the risk the task brief calls out by name — "the real risk that one of the two render paths forgets the fallback." Putting the fallback inside `buildNextStepsRows` rather than inside each renderer eliminates that risk structurally rather than by discipline: there is no second call site to remember, because there is no second place `why` is ever read from the raw `CarePlan` shape. A future third render path (there is no such plan today) would only need to call `buildNextStepsRows` like the other two to inherit the same guarantee for free.

### 4.7 Content-richness floor (PRD 04) — confirmed no guard needed

Covered in full in §4.3's `_log_thin_fields` walkthrough: `None` is falsy, the existing `if value and not _is_informative_quote(value):` guard already short-circuits on it exactly as it already did (and still does) for `""`, and `_is_informative_quote` is never called with `None` as its argument. No new guard, no signature change to `_is_informative_quote` (which remains typed for `str` and is never handed anything else).

### 4.8 Interface seam with PRD 14 (merge-provenance) — stated, not designed

PRD 14 adds `merged: bool` to the six item models and a MERGE prompt rule, editing the same two files this PRD edits: `backend/models/care_plan/care_plan.py` and `backend/care_plan/prompts/assemble_and_render.txt`. This PRD does not design PRD 14's field — the following is only what PRD 14's author needs to know about this PRD's edits to land cleanly alongside them:

- **`care_plan.py`**: this PRD adds one new field validator per class (`_normalize_why`, §4.1) to `Medication`, `Test`, `Procedure`, `OtherInstruction` only — it does not touch `FollowUp` or `WarningSign` (neither has a `why` field). PRD 14's `merged: bool` presumably lands on all six item models (it isn't scoped here). The two changes are field-independent — a new `bool` field and a new validator on an unrelated `str | None` field don't interact in Pydantic's validation order or in `model_json_schema()` output — but both PRDs touch the same class bodies, so whichever lands second will need a straightforward rebase (not a design conflict) if both are implemented in parallel.
- **`assemble_and_render.txt`**: this PRD rewrites the `NOT STATED --` paragraph (line 28) only. PRD 14's MERGE prompt rule is a separate, pre-existing paragraph (`MERGE --`, line 30, currently about combining duplicate facts into one item) that this PRD does not touch. The two paragraphs are adjacent but textually independent; no shared sentence needs to satisfy both PRDs' requirements.
- **`_diff_item`/`_PII_ELIGIBLE_FIELDS`**: a new `merged: bool` leaf would be compared by `_diff_item` exactly like any other unnamed leaf (equal → pass; unequal and unnamed → raise, since a `bool` is never `isinstance(..., str)` and so can never hit the PII branch). This PRD's `why`-nullability changes do not alter that behavior for a hypothetical `merged` field one way or the other — there is no shared code path between the two beyond `_diff_item`'s already-generic dict/list/scalar recursion, which needs no field-specific change for either PRD.
