# PRD 15 — Design-Doc Evidence Labeling

Parent brief: `docs/agent_files/2026-09-09-docs-fidelity-concision-brief/brainstorm.v1.md` (not re-litigated here). Comparison doc: `docs/agent_files/2026-09-09-docs-fidelity-concision-brief/comparison-drive-research-bundle.v1.md`, §5 R7 (this PRD's charter).
Branch: `docs/fidelity-concision-brief`.
Depends on: nothing. Touches no code, no schema, no prompt, no test.
Depended on by: 17 (scientific-documentation) should adopt the RF/DJ/PD vocabulary this PRD defines when it writes evidence-status prose in `docs/`; 16 (technical-documentation) may cite the constants register this PRD specifies (§4.3) wherever it documents a pipeline behavior gated by one of the listed constants. Neither dependency is a blocking one — both 16 and 17 are useful without this PRD landing; this PRD makes their evidence claims sharper if it lands first or alongside.

## 1. Problem

R7 of the comparison doc names a real, verifiable gap: the Drive research bundle tags every substantive claim RF (research finding, cited inline), DJ (product design judgment), or PD (proposed default, explicitly not evidence-calibrated), and carries a per-document evidence ledger mapping each claim to its source and role. This branch's nine landed PRDs do something adjacent — `[RESOLVED]`/`[OPEN]`/`[DEFERRED]` tags in every §9 — but that axis answers a different question. `[RESOLVED]` says a question is settled; it says nothing about *what kind of authority settled it*. Grepping the branch's own §9 items confirms the gap is real, not hypothetical: PRD 05 §9 resolves `_MAX_PII_TOKEN_DELTA = 4` in the same breath as it resolves the JSON-path addressing scheme and the soundness-over-completeness inversion — three `[RESOLVED]` items of visibly different epistemic weight, tagged identically. One is a number somebody picked (`_MAX_PII_TOKEN_DELTA`); one is an architectural synthesis of two cited papers plus this repo's constraints (soundness-over-completeness); the tag doesn't distinguish them.

The practical cost isn't abstract. `_MAX_PII_TOKEN_DELTA=4`, `_QUOTE_MIN_LENGTH=12`, `_QUOTE_LONG_WORD_MIN_LENGTH=7`, and `GLOSSARY_CURATION_TIMEOUT_S=20` are all honestly described in prose as reasoned-not-derived — but "honestly described in prose, somewhere in a 400+ line PRD" is not the same as "systematically findable." Nobody auditing this codebase for what's evidenced versus guessed can `grep` for an answer today; they have to read every PRD's §9 in full and manually classify each sentence. This PRD fixes that with two artifacts: a labeling convention for prose going forward (§4.1–§4.2), and a register that already exists, seeded, in this document (§4.3) — so the value doesn't wait on adoption discipline to compound over future PRDs.

## 2. Goals

- Define RF / DJ / PD precisely enough that two different people would apply the same label to the same sentence, demonstrated with three worked examples drawn from this repository's actual decisions (§4.1).
- Decide, with justification, where a label goes in a PRD — inline, in §9, or in a separate ledger table — rather than leaving it to each future author's taste (§4.2).
- Produce the uncalibrated-constants register as a concrete, complete-as-of-today artifact: its location, its columns, and full seed contents from an actual grep of `backend/` and the ten landed/in-batch PRDs that name a tunable (§4.3).
- Decide the retrofit question for the nine existing PRDs and for the comparison doc, with reasoning either way (§4.4).
- Say plainly how a future `dev-design` run would learn about this convention at all, and whether that requires touching anything outside this repo (§4.5).

## 3. Non-Goals

- **Not scientific/evidence documentation.** PRD 17 (scientific-documentation) writes user-facing `docs/` content explaining *why* the pipeline works the way it does, for someone new to the repo, citing the Drive research corpus. This PRD does not write that content and does not decide what belongs in it. This PRD defines the label vocabulary and the register format; 17 is a *consumer* of both, not the other way around. Concretely: if 17's prose says "grounding happens before generation because atomization-before-generation was shown to worsen hallucinations," that sentence and its RF/DJ split is 17's to write — this PRD only supplies the RF/DJ/PD words and the convention for where they go.
- **Not a retrofit of 01–09.** Addressed and argued in §4.4, not assumed here.
- **Not a new CI check, linter, or pre-commit hook.** See §7 — enforcement here is a human review habit, not tooling, and inventing tooling for a three-word vocabulary is exactly the process ceremony the initiative's locked decisions warn against.
- **Not a change to the `[OPEN]`/`[RESOLVED]`/`[DEFERRED]` status-tag convention.** That axis (decision status) and this PRD's axis (evidence provenance) are orthogonal and both stay — see §4.2's explicit statement of how they compose.
- **Not a change to any `backend/`, `frontend/`, or prompt file.** No constant's *value* changes as a result of this PRD; the register documents existing (and, for `_UNIT_WORD_MAX_LENGTH`, not-yet-landed) values, it does not calibrate them.

## 4. Architecture Decisions

### 4.1 The three labels — precise definitions and worked examples

Adopted verbatim in spirit from the Drive exemplars (`07-final-evidence-backed-pipeline.md`'s "How to read the recommendations", `05-clinical-safety-release.md`'s framing), reworded slightly for this branch's own voice:

> - **RF — Research Finding.** A claim directly reported by a cited source, with an inline citation, such that the sentence would be false (not merely unsupported) if the citation turned out to misrepresent the source. The test: could you rewrite the sentence as *"[source] reports [X]"* without changing its truth value? If yes, it's RF.
> - **DJ — Design Judgment.** An architectural or product conclusion that *reconciles* evidence (possibly RF-labeled evidence, possibly none) with this specific repository's constraints — no clinician in the loop, an anonymous single-shot upload, a fixed LLM-call budget, no durable state. No external source proposes the conclusion for this product; a person weighed tradeoffs and decided. The test: does the sentence contain a "because," "given," or "for this product" that connects an outside fact to an in-repo constraint? If the connective tissue is doing real work, it's DJ, not RF.
> - **PD — Proposed Default.** An implementation constant or threshold picked as a reasonable starting point, explicitly *not* validated against real data. The test: if you deleted the number and asked "how did you get this?", would the honest answer be "I reasoned about roughly what it should be" rather than "I measured it" or "an external source specifies it"? If yes, it's PD.

**Worked example 1 — RF.** PRD 05 §1: *"an LLM verifier bolted onto ungrounded prose largely rubber-stamps (38 invalid plans passed out of ~92 approved, [arXiv:2310.08118](https://arxiv.org/pdf/2310.08118))"*. This is RF: the 38/92 figure is Asgari et al.'s own reported result, not this project's measurement or judgment. Swap it for *"arXiv:2310.08118 reports 38/92"* and nothing changes. Note this sentence is *already written this way* in the landed PRD — the branch's authors already write RF-shaped sentences; they just don't mark them as such.

**Worked example 2 — DJ.** The brief's decision to invert the pipeline so that grounding (fact extraction with per-fact citations) happens before any generative writing pass, rather than generating prose first and verifying afterward — executed across PRDs 01–04, referred to throughout the branch's docs as "grounding before generation." This is DJ, not RF, even though it is directly motivated by RF-labeled evidence (worked example 1's rubber-stamping finding, plus the omission-detection-near-chance finding PRD 05 §1 also cites): no cited source tells *this product* to run a four-call pipeline of ground → assemble_and_render → review → correct under a 270-second internal deadline with no clinician reviewer. That specific architecture is this repo's own synthesis of the RF evidence against its own constraints (anonymous visitor, no account, no durable job state, single-shot upload — comparison doc §1). A second DJ example from the same family: the choice of clause-level `Fact` granularity (`{id, category, unit_id, char_start, char_end, text}`, one fact per clause — PRD 01/03) over the Drive bundle's atomic-with-attributes shape (comparison doc §4.2) — both readings cite the same Asgari finding about atomization risk, and *from the same evidence* this repo's authors drew a narrower-scope conclusion suited to a product with no clinician calibration loop. Same evidence, different DJ, because DJ is where evidence meets *this* repo's specifics.

**Worked example 3 — PD.** `_MAX_PII_TOKEN_DELTA = 4` (`backend/care_plan/pipeline.py:530`, resolved in PRD 05 §4.6/§9). The PRD's own words: *"4 was chosen to comfortably cover a full name plus title while staying well short of what a genuine sentence-level rewrite would produce, but it has not been calibrated against real notes."* Nobody measured a distribution of real PII-substitution diffs and picked the 95th percentile; somebody reasoned about what a plausible name-swap word-count looks like. That is PD by definition — and note the PRD text was already honest about this before this convention existed; the label only makes the honesty greppable.

These three examples are chosen specifically because they are hard to confuse with each other on a casual read — a future author asked to label a new PRD sentence should reach for this section, not the abstract definitions alone.

### 4.2 Where labels go

**Decision: inline, at the point of the claim, as a short parenthetical suffix — not a separate per-document ledger table, except for citation-dense documents (defined below).**

Concrete form:

```markdown
An LLM verifier bolted onto ungrounded prose largely rubber-stamps (38 invalid plans
passed out of ~92 approved, [arXiv:2310.08118](https://arxiv.org/pdf/2310.08118)). (RF)

This is why grounding runs before any generative pass in this pipeline — no cited
source specifies this exact architecture for an anonymous, single-shot, no-clinician
product, but the RF above forecloses "verify after the fact" as adequate here. (DJ)

`_MAX_PII_TOKEN_DELTA = 4` is a reasoned starting point, not calibrated against real
notes (`backend/care_plan/pipeline.py:530`). (PD)
```

Justification against the two alternatives considered:

- **Against a separate ledger table for every PRD.** The Drive exemplars are stand-alone research memos with no dependent code and no §9 status-tag machinery of their own; a ledger table is their *only* mechanism for surfacing evidence provenance. This branch's PRDs already carry a heavier structural apparatus (numbered §9 items, `[RESOLVED: ...]` decision records, cross-PRD coupling tables in `prds/README.md`). Requiring a second table that must stay in sync with prose through the same kind of "resolved every `[OPEN]` item, reconciled cross-references after concurrent edits" revision passes `prds/README.md` describes for 01–08 is a second source of truth that will drift the first time someone edits a claim's wording without touching the table. Inline tags can't drift the same way because they live in the sentence itself.
- **Against tagging only in §9.** Most of a PRD's substantive claims live in §4 (Architecture Decisions), not §9 — §9 is where *open or resolved decisions* get recorded, and plenty of §4 prose (rationale paragraphs, worked comparisons, cited-evidence sentences) never becomes a numbered §9 item at all. Confining labels to §9 would silently exempt the majority of a PRD's claims, including exactly the RF-cited sentences in §1/§4 that motivated R7 in the first place (see PRD 05 §1, unlabeled today, itself already RF-shaped).
- **Cost check.** Existing PRDs already write citations and rationale inline (PRD 05 §1's own sentence is the demonstration). Appending `(RF)`/`(DJ)`/`(PD)` to a sentence that already exists costs a few characters of typing discipline, not a new writing task. This satisfies the "resist inventing process ceremony nobody will follow" instruction better than any table-based scheme would.

**Exception — the evidence ledger, for citation-dense documents only.** A document built primarily as a survey of external evidence against this repo (the comparison doc is the only current example; a future PRD 17 scientific-documentation page might be another) benefits from the Drive exemplars' actual ledger table — not because inline tags are insufficient there too, but because a reader of a document with dozens of citations needs a single place to see the whole evidence-to-claim mapping at a glance, the way `05-clinical-safety-release.md`'s own "Evidence ledger" section works. Rule of thumb, not a hard trigger: if a document cites three or more distinct external sources, add a ledger table (same four columns as the Drive exemplar: claim/decision, source and location, support and limitation) in addition to, not instead of, inline tags. An ordinary sub-project PRD like 01–14 will essentially never cross this threshold — they cite the same two or three papers repeatedly, not a dense external bibliography — so this exception is expected to apply rarely.

**Relationship to `[OPEN]`/`[RESOLVED]`/`[DEFERRED]`.** Fully orthogonal, both kept. A `[RESOLVED: ...]` item in §9 can and often will carry an RF/DJ/PD tag on the sentence(s) inside it, exactly as PRD 05's `_MAX_PII_TOKEN_DELTA` item already *narrates* PD in prose without the literal tag. Status says "is this settled"; RF/DJ/PD says "what kind of authority settled it." Both axes can and should appear on the same sentence: `[RESOLVED: _MAX_PII_TOKEN_DELTA stays 4] (PD)`.

### 4.3 The uncalibrated-constants register

This is the artifact that makes the PRD worth implementing even under loose adoption of the labeling convention itself — it is complete as written here, not a promise to fill in later.

**Location.** A new standalone file, `docs/uncalibrated-constants.md`, created when this PRD is implemented (a `dev-tasks`/`dev-code` documentation task, not a write this PRD makes itself). Not inside `docs/agent_files/...`: that directory is this branch's dated design-session workspace (per this machine's own memory convention: "design docs go in `docs/agent_files/<date>-<branch>/`, not scattered by type") — a point-in-time record of *how a decision was reached*, not living reference material meant to track the *current* state of the code as constants are added, tuned, or retired. `docs/uncalibrated-constants.md` sits alongside `docs/pipeline.md`, `docs/architecture.md`, etc. — the durable, current-state documentation set PRD 16 is rewriting — because that is where a future engineer changing a constant, or PRD 17 citing one, would actually look. PRD 16 should link to it from `docs/pipeline.md` wherever a documented pipeline step depends on one of these constants; PRD 17 should cite it as the place uncalibrated numbers live rather than re-deriving the same rationale in its own prose.

**Maintenance rule** (stated here so it isn't reinvented per-PRD): any future PRD that introduces or changes a numeric constant explicitly described as reasoned-not-measured adds or updates a row in this file as part of that PRD's own scope — the same way PRD 10 (below) would have, had this PRD landed first.

**Columns:**

| Column | Meaning |
|---|---|
| Constant | The literal name as it appears in code |
| Value | Current value |
| Defined in | `file:line` (or PRD name, for a not-yet-landed one) |
| What it controls | One-line functional description |
| Why this value | The reasoning given when it was picked, and its PRD/section source |
| How it would be calibrated | The concrete measurement that would turn PD into something evidence-backed, if run |
| Owner (PRD) | Which sub-project's scope the constant belongs to |

### 4.4 The retrofit question

**Decision: retrofit nothing among PRDs 01–09. Retrofit the comparison doc (`comparison-drive-research-bundle.v1.md`) — but only its own §5 recommendations table and evidence-heavy sections, and only if the owner wants the citation-dense document to model the convention it recommends, not as a requirement of this PRD.**

Argument for leaving 01–09 alone: they are `prds/README.md`'s own words, "settled" and "implemented" — `grep -rn "\[OPEN" prds/` already returns nothing live. Adding RF/DJ/PD tags to nine PRDs totaling 4,543+ lines would touch prose that has already been reviewed, revised across a reconciliation pass, and shipped as code, for a benefit that is purely retrospective legibility — nobody is deciding anything in those documents anymore. The register in §4.3 already extracts the one thing from 01–09 that has ongoing value (the uncalibrated constants themselves, with citations back to the PRDs that reasoned about them) without touching the PRDs' prose at all. This matches the explicit instruction in this PRD's brief: retrofitting is "almost certainly not worth it."

Argument for the comparison doc as the one exception, stated but not acted on here (out of scope — this PRD does not edit that document): it is the newest, most citation-dense document on the branch, it is the document that *names* R7 and the RF/DJ/PD convention in the first place, and unlike 01–09 it makes exactly the kind of claim (comparing this repo's choices against external evidence) that RF/DJ/PD exists to disambiguate — its own §4.1 "reasoned default vs. guessed number" paragraph (quoted in this PRD's §1) is a direct, un-tagged instance of the confusion R7 diagnoses. Applying the convention there would be a proof-of-concept in the one place on this branch where the vocabulary earns its keep immediately. Left as `[OPEN]` (§9) rather than decided, since editing that document is arguably outside this PRD's own "touches no existing doc" boundary — the owner should decide whether it's worth a small follow-up edit to that specific file.

## 7. Testing

There is no code to test. Being honest about what "testing a convention" means, rather than inventing ceremony:

- **No CI check, no linter, no pre-commit hook.** A regex that flags un-tagged claims would have a near-100% false-positive rate against ordinary prose (most sentences in a PRD are neither RF, DJ, nor PD — they're plumbing: "this method takes X and returns Y") and would train authors to add meaningless tags to satisfy a tool rather than to communicate. This is the same reasoning the PRD's own Non-Goals give for not building tooling around a three-word vocabulary.
- **The actual check is a human review step, and it already exists.** `dev-review`/`dev-critique` (and, before those, the human PRD-approval gate `dev-design` stops at) is where a reviewer reading a new or substantially-revised PRD can ask "is this claim RF, DJ, or PD, and does the label match?" — the same way a reviewer today already checks whether a `[RESOLVED]` item's reasoning holds up. Adding "and is the evidence label right" to that existing checklist costs nothing new to set up.
- **The register (§4.3) is the one artifact with a concrete acceptance check**: does `grep -n "_QUOTE_MIN_LENGTH\|_MAX_PII_TOKEN_DELTA\|GLOSSARY_CURATION_TIMEOUT_S\|_MAX_LONG_EDGE_PX\|_UNIT_WORD_MAX_LENGTH" backend/` (once PRD 10 lands) return exactly the six constants this table lists, with no orphans on either side? That is a real, mechanical check — but it is a one-time content-freshness check to run when `docs/uncalibrated-constants.md` is created and whenever a PRD adds a new tunable, not a standing test.
- **No acceptance criterion of "X% of claims are labeled."** Nobody is going to retroactively count. The convention succeeds if the next PRD that makes a citation-backed or admittedly-arbitrary claim tags it; it does not need a metric to be worth adopting.
