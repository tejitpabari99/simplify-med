## Follow-ups / new issues discovered

- **`input_provenance` growth is not bounded the way PRD §4.13 assumes.** `resolve_uploaded_files` emits one `SourceSpan` per (file, page), and no page-count ceiling exists anywhere. `MIN_MEANINGFUL_CONTENT_CHARS` (= 20) is checked against the whole file's combined text, not per page, so a PDF of many nearly-empty pages stays under `MAX_AGGREGATE_FILE_BYTES` (10 MB) and `MAX_TEXT_BYTES` (350,000) while generating far more spans than §4.13's 500-span estimate. At the extreme the processing-state Firestore document could exceed the 1 MiB hard limit, making `create_job_doc`'s `.set()` fail with an unhandled exception rather than a clean validation error. Note the mitigating context: **PRD 09 (input-transport) moves `input_text` and `input_provenance` off Firestore into a GCS object entirely**, which dissolves this failure mode — but 09 lands last, after 03-08. Nothing is deployed in the interim (global no-deploy constraint), so the exposure is confined to local testing. Decide whether to add an explicit span-count ceiling with a clean `ErrorCode` now, or accept it until 09. This is a PRD-level decision, not a code fix to make silently.
- Minor: `complete_job`'s docstring in `utils/firebase.py` now introduces two fields but a trailing clause still reads singular ("the raw ... text is write-once"). Cosmetic.
