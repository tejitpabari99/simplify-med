## 1. Problem

The owner's own framing, verified against the actual repository state rather than assumed: **the entire `docs/` tree documents a pipeline that no longer exists.** This is not an exaggeration for effect — every one of the five files in `docs/` plus the root `README.md` contains at least one factually false sentence about the current system, verified below by reading the actual current code (`backend/care_plan/pipeline.py`, `backend/utils/constants.py`, `backend/models/job.py`, `backend/services/care_plan_input.py`, `backend/routes/jobs.py`, `backend/routes/worker.py`, `backend/models/provenance.py`) against every claim in every doc file, line by line.

### 1.1 The core factual error, repeated in five places

The real pipeline today is **four sequential LLM calls** — `ground` → `assemble_and_render` → `review` → `correct` (`backend/care_plan/pipeline.py:828-963`, `Constants.Pipeline.PIPELINE_STEPS` in `backend/utils/constants.py:62-76`) — plus a deterministic unitizer (`backend/services/unitizer.py`), deterministic term detection, three deterministic post-checks inside `assemble_and_render`'s `_verify_assembly` (citation existence, question-count cap, content-richness logging), a background glossary-curation thread running concurrently with steps 3–6, and a deterministic close (glossary re-detection). Six user-facing progress steps (`Constants.Pipeline.PIPELINE_STEPS`: `READ_NOTE`, `DETECT_TERMS`, `GROUND`, `ASSEMBLE_AND_RENDER`, `REVIEW`, `CORRECT`).

Every doc file instead describes the pre-inversion pipeline PRDs 04/05/06 deleted: five stages, three Gemini calls (`simplify_language` → `clarify_and_action` → `structure_note`), computed via three prompt files that **no longer exist on disk**:

```
$ ls backend/care_plan/prompts/
assemble_and_render.txt  correct.txt  curate_glossary.txt  ground.txt  review.txt  _style_rules.txt
```

`simplify_language.txt`, `clarify_and_action.txt`, `structure_note.txt` are gone. `docs/pipeline.md` still names all three as if they were live:

> `docs/pipeline.md:104`: "**Prompt** (`care_plan/prompts/simplify_language.txt`): rewrite the note to roughly a 6th-grade reading level..."
> `docs/pipeline.md:115`: "**Prompt** (`care_plan/prompts/clarify_and_action.txt`): rewrite in active voice..."
> `docs/pipeline.md:126`: "**Prompt** (`care_plan/prompts/structure_note.txt`): return JSON only..."

A reader who opens `pipeline.md` to understand what a document goes through, then goes looking for `simplify_language.txt` to see the actual prompt text, will not find it — because it was deleted by PRD 04, and the fields it produced (`simplified`, `clarified` on `PipelineRunResult`/`AdapterResult`) were deleted outright by PRD 06 §4.5 with nothing replacing them.

### 1.2 Why this is not cosmetic — the external-review harm

`docs/agent_files/2026-09-09-docs-fidelity-concision-brief/comparison-drive-research-bundle.v1.md`, an external research review commissioned specifically to critique this product's clinical-fidelity design, used `docs/pipeline.md` as its **"repository baseline"** for what the pipeline does. Concretely: R2 (numeric integrity, now PRD 10), R1 (omission signal, now PRD 11), and R4 (extraction provenance, now PRD 12) all cite the old five-stage/three-call description as their premise — critiquing the product for defects **this branch had already fixed** at the time the review ran, because the docs still said the old pipeline was live. `_STYLE_RULES`'s numeracy gaps, the discarded `review().coverage` field, and the untagged OCR units are all real, still-open gaps this batch's PRDs 10–12 correctly identify — but the review reached them by reading a document that, for the pipeline shape itself, was already wrong. A stale `docs/pipeline.md` did not just fail to help; it actively fed a serious external analysis a false premise about what code was running. This is the single strongest argument in this repository for treating documentation rot as an engineering defect, not a tidiness backlog item — a wrong architecture doc is not neutral, it is actively misleading input to whoever reads it next, human or agent.

## 3. Non-Goals

- **Not the evidence/why layer.** PRD 17 (scientific-documentation) owns explaining *why* the pipeline is designed the way it is — the research corpus (AgenticSum, Asgari et al., Croxford/PDSQI-9, Fact-Controlled Diagnosis, the AHRQ Toolkit), how well-evidenced each design choice is, and a "good summary criteria" conformance table. This PRD documents **mechanism**: what each component does, its data shapes, its call sequence, its failure modes — never "how well-evidenced is this." The precise line, and the citation convention between the two families, is in §3 below (yes, this Non-Goals section names its own boundary section — see the worked rule immediately following).

  **The operational rule**: if a sentence's truth value depends on a cited external source or a comparison against a published instrument (PEMAT, SAM, CDC CCI, the Drive research corpus), it belongs in 17, and this PRD's docs cross-reference it rather than restating it. If a sentence's truth value depends only on reading the code (what function is called, what field exists, what happens on failure), it belongs here. Concretely: "the pipeline runs `ground` before `assemble_and_render`, which is fatal on failure" is 16's; "grounding runs before generation because atomization-before-generation was shown to worsen hallucination rates" is 17's — same architectural fact, but the *why* clause is the tell. Where a technical doc under this PRD needs to gesture at a design rationale (e.g. "review is non-fatal by design — see `docs/<17's-doc>.md` for why"), it states the mechanism and links out; it never re-derives or restates the evidentiary argument itself.

  **The reconciled cross-reference convention** (binding on both PRDs; reconciled with 17's independently-proposed blockquote form — see §9): the two proposals turned out not to conflict, because they operate at different granularities, and forcing either to do both jobs is what made them look inconsistent.

  **Inline is the default**, used for a cross-reference attached to a specific claim or sentence. A technical doc (this PRD's family) links to a scientific doc (17's family) with the phrase pattern `— see [<doc>.md](<doc>.md) for why` immediately after stating the mechanism, never before it (mechanism first, evidence-pointer second, so a reader who only wants "what happens" never has to skip past a citation to find it). A scientific doc links back to a technical doc with `— see [<doc>.md](<doc>.md) for the exact mechanism` when it needs to ground an evidentiary claim in a specific function or check. The asymmetric wording makes the direction of every link self-describing. Neither family duplicates the other's prose; a link plus one clause of context (what the reader will find there) is the whole inline convention.

  **The blockquote form (17's proposal) is reserved for orientation signposts** at the head of a document or a major section, where the whole unit's counterpart lives in the other family — exactly the use 17 §4.2's README sample demonstrates (its closing pointer into `../pipeline.md`/`../architecture.md`). It is never used mid-prose for an individual claim; that case always uses the inline form above. Most cross-references in this doc family are the incidental, single-sentence kind — a blockquote for each would shred the prose — so inline is the default and the blockquote earns its place only once per document/section, where a reader arriving needs to be told, once, where its other half lives.

  Target filenames for 17's family, settled now that 17 exists: five files under `docs/science/` — `docs/science/README.md`, `docs/science/design-rationale.md`, `docs/science/good-summary-conformance.md`, `docs/science/evidence-map.md`, `docs/science/research-corpus.md` (17 §4.1). This PRD's own docs' links into 17's family are written against these exact paths.

## 4. Architecture Decisions

### 4.0 Sequencing — document the post-01-18 state, after 10–18 land, not the post-01-09 state

**This section originally recommended writing the doc rewrite now, against the post-01-09 state, and treating 10–15 as a distant future amendment. The owner has since decided differently — wait — and that reverses this section's decision. The reasoning below is kept, not deleted, because two of its three original reasons are still correct; only the premise underneath reason 3 changed. Read this section as a record of what changed and why, not a silent rewrite of history.**

**The ordering problem, stated precisely — updated.** PRDs 01–09 are implemented and landed (verified throughout §1.3 by reading the actual code). PRDs 10–18 are written, reviewed to the same house standard, and — as of this amendment — **about to be implemented immediately, in one batch**: `TASKS.md` exists for all nine (10 through 18), and a `dev-code` run against them is starting now. As of this writing no code in `backend/` yet reflects any of them (still verified true: `grep -rn "extraction_method\|NUMERACY\|_UNIT_WORD_MAX_LENGTH"` against `backend/` returns nothing; `Medication.why` is still `str = ""`, not `str | None`, per `backend/models/care_plan/care_plan.py:34` — re-checked at the time of this amendment). What changed is not the current code, it's the timeline: 10–18 are no longer an indeterminate-future maybe, they are the very next thing to land.

**Decision (reversed from this PRD's original recommendation): the doc rewrite waits for PRDs 10–18 to land, and documents the post-01-18 state.** It does not ship now against the post-01-09 state, and it does not speculatively describe 10–18 as a future amendment to an already-shipped doc set — by the time this PRD's docs are actually written, 10–18's fields, log lines, and prompt rules will be real, checked-out code, not a forecast. What changed since the original decision, reason by reason:

1. **Unchanged principle, now arguing the other way.** "A doc that describes code that doesn't exist yet is exactly as wrong as a doc that describes code that no longer exists" — both fail the one test that matters ("does this match what I'd find by reading `backend/`"). This was the reason to write *now* when 10–15's landing was indeterminate and possibly far off; it is now the reason to *wait*, because 10–18 are landing imminently and writing today would guarantee the freshly-written doc starts describing a state (post-01-09) that stops matching checked-out code within, at most, one `dev-code` pass. The principle didn't change; which direction it points did, because the premise about *when* 10–18 land changed.
2. **The forward-reference inventory survives, but changes role — from "later amendment" to "required initial content."** Under the old assumption, 10–18's additions (a NUMERACY paragraph in the pipeline doc's `_verify_assembly` section for PRD 10, a new `Literal` value and sentence in the data-model doc for PRD 12's `extraction_method`, a one-line nullability note for PRD 13's `why: str | None`, and more besides) were framed as small, targeted amendments to an *already-shipped* document, made later, one at a time, as each PRD landed. Under the new decision, none of that content is written twice — it is simply *in* the doc from the first draft, because 10–18 are already-landed code by the time that draft is written. §4.1's per-file specs are updated accordingly (see the full inventory below), and every target doc's initial version must include it, not amend it in afterward.
3. **This reason is now false, and it was the load-bearing one.** The original §4.0 argued that "deferring the doc rewrite until 10–15 land compounds the exact problem this PRD is fixing," because `docs/` would stay silent about the real four-call pipeline "for the entire duration of five more implementation passes, each of which is itself a multi-day-to-multi-week `dev-code` effort." That claim is what made "write now" the right call — and it is no longer true. 10–18 are not five-to-nine separate, unscheduled implementation passes stretched over an unknown span; they are one batch, with `TASKS.md` already generated for every one of them, about to be executed together in a single `dev-code` run. There is no long compounding window for `docs/` to sit silently wrong in the other direction — the wait is one batch, not five-to-nine indefinite ones. With the compounding-cost reason gone, reason 1's unchanged principle is left standing alone, and it now points at waiting: shipping the doc rewrite today would create a document that is stale on arrival, which is the exact defect this whole PRD exists to eliminate.

3. `POST /jobs` reaches `simplify-api` — `_resolve_job_input` extracts text, builds `SourceSpan` provenance, writes the GCS `JobInputPayload` — one paragraph, links to `architecture.md` §2 for the exact object shape.

7. Worker picks up the task, verifies OIDC, checks the processing lease — one paragraph, links to `architecture.md`'s idempotency section.

9. Term detection runs; the glossary-curation thread starts in the background — one paragraph.
10. The four LLM calls run in sequence, each writing a `stage` update the frontend's listener picks up live — one paragraph per call is **too deep for this document**; one paragraph for all four, with the mermaid diagram (below) carrying the sequencing, and a link to `pipeline.md` §4 for depth.
11. The deterministic close (glossary re-detection); `output_data` assembled, internal fields stripped (`_strip_internal_provenance`) — one paragraph.
12. `complete_job` writes the terminal Firestore update; both GCS objects are deleted in the worker's `finally` block — one paragraph.
13. The frontend's listener sees the terminal state, renders `ResultScreen.tsx`/`CarePlanView.tsx`, fires `DELETE /jobs/<job_id>` the instant it mounts — one paragraph, links to `data-and-privacy.md`'s deletion-path table for the full backstop chain.

It must show, precisely:
- The `POST /jobs` call and its two possible GCS writes (payload always, merged PDF only for uploads) as a note on the `simplify-api` lifeline, not a separate participant.
- The Firestore job-doc creation and the Cloud Task enqueue as two distinct arrows from `simplify-api`, both before the `202` response returns to `Browser` — this ordering (config validated and both writes done before responding) is a real, load-bearing property (`architecture.md`'s "never orphans a doc" guarantee) and the diagram should make it visually obvious that the `202` comes *after* both.
- A loop/loop-like block on the `simplify-worker` lifeline representing the four-call pipeline, each iteration writing a `stage` update back to `Firestore` — collapsed to one labeled block ("ground → assemble_and_render → review → correct, writing stage 3-6"), not four separate LLM call arrows, to keep the diagram at flow-level altitude.

### 4.6 Accuracy mechanism — what actually gets maintained

**The precedent already in this codebase**: `backend/tests/integration/test_dead_code_removed.py` (§1, verified by reading) already asserts, mechanically, that specific deleted modules stay deleted (`utils.vertex_ai`, `utils.pdf_extract`, etc., each via `ModuleNotFoundError`) and that no stray `.py` file reappears at `backend/` root. This is the exact shape of check this PRD needs, aimed the other direction: not "assert the old thing is gone" but "assert the doc's claims about the current thing are still true."

**Proposed: one new test file, `backend/tests/integration/test_docs_reference_real_symbols.py`**, three narrowly-scoped checks:

1. **Every prompt filename `docs/pipeline.md` names in backticks must exist in `backend/care_plan/prompts/`.** Concretely: parse `docs/pipeline.md` for the regex `` `care_plan/prompts/([a-z_]+\.txt)` ``, and assert every match is a real file under `backend/care_plan/prompts/`. This is the exact test the task brief asked to consider, and it would have caught this PRD's entire §1.1 finding on day one of PRD 04 landing, had it existed then. Cheap, mechanical, zero false positives (a filename either exists or it doesn't), and it degrades gracefully — if a future author renames a prompt file and forgets the doc, this test fails with a clear message naming the missing file, not a vague doc-drift complaint.
2. **Every `Constants.Pipeline.PIPELINE_STEPS` member name `docs/pipeline.md`'s step table names must match the live enum**, by importing `Constants.Pipeline.PIPELINE_STEPS` and asserting its member count and each member's `.label` string appear verbatim in the doc's step table. This catches the single failure mode most responsible for the current rot (a pipeline restructure that changes step count/labels without a doc follow-up) directly, mechanically, at the exact seam PRD 06 already treats as load-bearing (its own `ProcessingScreen.tsx`/`markers.py`/`firebase.py` sync obligations, PRD 06 §4.1/§4.7).
3. **Every field name `docs/architecture.md`'s job-doc table names must be a real field on `JobDoc`**, via `JobDoc.model_fields.keys()` — catches the exact class of error this PRD's own audit found twice (`input_text` documented as existing when it doesn't).

**What this does NOT attempt, and why.** No check that prose *describing* a mechanism is accurate (e.g. "grounding is fatal on failure" — verifying this mechanically would require parsing English against `iter_steps`'s exception-handling structure, which is not a tractable, low-false-positive check) — that class of drift is caught by human review (the `CONTRIBUTING.md` checklist item below), not a test. This mirrors PRD 15 §7's own reasoning for its convention (no linter for prose, because a prose-correctness linter has a near-100% false-positive rate against ordinary technical writing) — the three checks above are chosen specifically because each is a **symbol-existence** check (a filename, an enum member, a model field), not a semantic one, which is exactly the class of drift that is both mechanically checkable and, per this PRD's own audit, the class that actually happened three times over in this repository's history.
