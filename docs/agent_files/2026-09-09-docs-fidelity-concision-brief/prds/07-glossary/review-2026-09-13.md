**Verdict: approve-with-fixes**

The keying-bug fix, stoplist prune, `render_care_plan_text` field projection, and `build_glossary_from_care_plan` are all correct, match the PRD, and are covered by tests that were run and pass (`44 passed` for `tests/utils/test_jargon_db.py tests/utils/test_term_detection.py tests/scripts/test_prune_jargon_stoplist.py`, `--noconftest`, from `backend/`). ## Findings

| High | `backend/utils/term_detection.py:198-241` (specifically the `for item in propose:` loop, 211-230, and the `get_source_name` call at 226) | `curate_glossary_terms` does not validate the *shape* of the LLM's parsed JSON before iterating it, so a syntactically-valid-but-wrong-shaped response crashes with an uncaught exception, violating the function's own docstring ("Must never raise: a curation failure falls back to the deterministic list untouched") and PRD §4.3's identical claim. Only the `client.generate_json(...)` call and the top-level `isinstance(raw, dict)` check are inside the `try/except Exception` (lines 188-204); everything from line 206 on — including the loop over `raw["propose"]` and the `.get()` calls on each item — runs unguarded. | Reproduced directly by stubbing `LLMClient.generate_json` to return shapes that satisfy `isinstance(raw, dict)` but aren't otherwise well-formed: `{"drop": [], "propose": ["circumflex"]}` → `AttributeError: 'str' object has no attribute 'get'`; `{"drop": [], "propose": None}` → `TypeError: 'NoneType' object is not iterable`; `{"drop": [], "propose": {"a": 1}}` → `AttributeError: 'str' object has no attribute 'get'` (iterating a dict yields its keys). All three propagate out of `curate_glossary_terms` uncaught — verified by direct script execution against the real function. This is exactly the scenario the task's own review brief asks about ("does it trust LLM-proposed terms/definitions blindly?") — the answer is: it partially validates well-formed items (non-empty `matched_term`/`definition`, substring-in-source guard) but not the *shape* of `propose`/its items, and a shape violation is worse than being ignored — it crashes the caller. Since 06 is expected to submit this to a `ThreadPoolExecutor` and treat it as fire-and-forget/non-fatal (PRD §4.3, §9), an uncaught exception here either surfaces unexpectedly whenever the future's result is consumed, or is silently swallowed depending on 06's wiring — either way it defeats the fail-open design this whole function exists to provide. | Wrap the whole function body (through the `return combined` at the end) in one `try/except Exception: return detected_terms`, or at minimum validate defensively before the loop: `if not isinstance(propose, list): propose = []` and `if not isinstance(item, dict): continue` inside the loop. Add a regression test with `generate_json` returning `{"drop": [], "propose": ["not-a-dict"]}` (or `propose: None`) asserting the function returns `detected_terms` unchanged instead of raising. |
| Medium | `backend/utils/term_detection.py:232-240` | The `_CURATION_TOTAL_BACKSTOP` (40) truncation only ever slices `proposed_hits`; if `kept` alone (deterministic hits surviving the LLM's own drop-filter) already exceeds 40, `overflow` is still computed and a `"truncating N total terms to backstop 40"` warning is logged, but since `proposed_hits` is already at or below the required cut, the slice is a no-op and `combined` is returned still over the backstop. This contradicts PRD §4.3's explicit claim that `_CURATION_TOTAL_BACKSTOP` is "code-enforced, covering `kept + proposed_hits`" — it is enforced only when `proposed_hits` alone is large enough to absorb the whole overflow. | Reproduced directly: 45 synthetic `kept` entries, stub returns `{"drop": [], "propose": []}`; the code logs `"truncating 45 total terms to backstop 40"` but `len(result) == 45` (not 40). Task 10's own backstop test (`test_curate_glossary_terms_backstop_truncates_proposed_before_kept`) only exercises the 35-kept/10-proposed case where `kept <= backstop`, so this gap isn't caught by the existing suite. | Either truncate `kept` too once `proposed_hits` is exhausted (`combined = combined[:_CURATION_TOTAL_BACKSTOP]`, applied after building `kept + proposed_hits` and cutting from the end, or from `kept`'s tail if "cut proposed first" must still hold when both are large), or downgrade the log message/docstring to be honest that the backstop only bounds `proposed_hits`' contribution, not the deterministic list's own count. Given `kept` is already curated by the LLM's own drop pass, this is a low-likelihood-in-practice edge case (needs 40+ dictionary hits surviving curation on one note) but the current code's claim of enforcement is simply false when it fires. |

## Verified correct (left alone)

- **Keying bug fix** (`backend/utils/jargon_db.py:279-300`, `build_terms_glossary`): keys strictly on `hit["matched_term"]` (KeyError on a caller that omits it, matching PRD §9's resolved decision, not a silent `.get()` fallback). Confirmed against both `lookup_medical_terms` (`jargon_db.py:218-250`, always sets `matched_term`) and `curate_glossary_terms`'s proposed-hit construction (always sets `matched_term == term`).
- **`get_source_name` rename** (`jargon_db.py:50-56`): public, all three in-module call sites (`_plain_language_rows`, `_medical_rows`, `_abbreviation_rows`) updated; `grep -rn "_get_source_name" backend --include=*.py` and `grep -rn "build_glossary_from_simplified_text" backend --include=*.py` both return zero hits outside `backend/care_plan/pipeline.py` — the one disclosed, out-of-scope gap the PRD/TASKS explicitly hand off to PRD 06 (not reported per instructions).
- **Stoplist prune** (`backend/scripts/prune_jargon_stoplist.py`): parenthetical-exemption and comma-branch semantics match PRD §4.2 exactly; the later fix commit `50757fa` correctly identified and closed a real gap (stoplist entries that are themselves comma-lists, e.g. `"foot, feet"`, were never being split before comparison) with its own regression test (`test_prune_drops_record_when_stoplist_entry_itself_has_commas`) and a re-run against the real dictionary (1949→1948 records, `"foot, feet"` the only additional drop). Verified the committed `michigan_medical_dictionary.json` no longer contains any of the 14 stoplist words/entries as bare canonical terms.
- **Prompt brace hazard**: `curate_glossary.txt`'s JSON-schema example line correctly double-escapes its literal braces (`{{"drop": ...}}`); confirmed by calling `.format(max_terms=15, detected_terms_block="x", source_text="y")` directly against the checked-in file with no error. No other unescaped single-brace literal exists in the file.
- **`render_care_plan_text` field coverage** (`term_detection.py:90-141`): compared field-by-field against `backend/models/care_plan/care_plan.py`'s `CarePlan` and all its nested item models — every free-text, patient-visible field is rendered (`summary`; `reason_for_visit.{reason,description}`; `diagnosis.changed_since_last_visit` and `details.{title,plain_name,description,what_it_means_for_you}`; all ten `Medication` text fields including `change`; `tests`/`procedures`/`other`/`follow_up`/`warning_signs`' text fields; `questions`; `low_priority`). Internal/non-patient fields are correctly *excluded*: `note` (confirmed zero frontend consumers via `grep` on `CarePlanView.tsx`), `summary_fact_ids`/`source_fact_ids` (int lists), and the typed enums `status`/`severity`/`urgency`. No gap found in either direction.
- **`build_glossary_from_care_plan`**: logic-identical to the deleted `build_glossary_from_simplified_text`, routed through `render_care_plan_text` first, as specified; re-detection correctly finds a term whose only occurrence is in a nested `diagnosis.details[...].description` (Task 10's own test, passing).
- **Prompt-injection / PHI surface**: the clinical note (`source_text`) is interpolated directly into `curate_glossary.txt` via `str.format`, an intentional, PRD-acknowledged design (§9's resolved decision not to route curated output through the fidelity reviewer). Checked all `logger.*` call sites in `jargon_db.py`/`term_detection.py` (`jargon_db.py:115,162,182`; `term_detection.py:59,66,73,76,203,234`) — none log prompt content, `source_text`, or LLM raw output; only counts and static messages. Model-proposed `definition`/`term` values reach the frontend as plain React text nodes (`CarePlanView.tsx:297-298`, no `dangerouslySetInnerHTML`), so no XSS surface even from an adversarial note. Residual risk (already named and accepted in PRD §9, not re-litigated here): an injected instruction in the note could steer the model toward a misleading-but-plausible "definition" that isn't reviewed by the fidelity reviewer — a content-integrity risk, not a code defect.
- **Architecture fit**: `_format_detected_terms_for_curation` (term_detection.py:162-167) duplicates the shape of `format_medical_terms_for_prompt` but is justifiably distinct (needs the definition, the assembly-prompt formatter doesn't) — minor, acceptable duplication, not worth collapsing. `curate_glossary_terms` is a free function as specified (not a `CarePlanPipeline` method), constructs its own `LLMClient` when none injected, matching the `score_text_safe` background-thread precedent. No dead code left behind in this PRD's own files.
