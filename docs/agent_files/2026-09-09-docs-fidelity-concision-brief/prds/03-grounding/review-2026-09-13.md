# Independent review: PRD 03 (Grounding), diff `f21b78b..HEAD`

Reviewer: independent pass, read-only (no code changes). Scope: the 9-commit diff implementing PRD 03, against `PRD.md` §4.1–§4.7/§9 and `TASKS.md`.

## Verdict

**Blocking issues found.** The anti-fabrication guarantee that is this PRD's central purpose (`_is_verbatim_quote` / `_locate_quote_offsets`) has a concrete hole: a quote made of characters that `normalize_text` strips to nothing passes the verbatim check vacuously and, in `_locate_quote_offsets`, resolves to the entire cited unit's text (or crashes with an `IndexError` if the unit's text is empty). A fabricated fact can survive all three deterministic checks and be attached to a whole unit as its "verified" evidence.

Everything else — prompt fidelity, non-goal boundaries, id assignment/renumbering, drop policy, fatal/non-fatal behavior, and every other offset-recovery edge case I traced (multi-space runs, tabs, newlines, leading/trailing whitespace, dropped non-ASCII characters, ligature expansion in the ordinary case, repeated occurrences, empty/all-whitespace units, quote boundaries adjacent to a collapsed whitespace run) — is correct and matches the PRD. All 608 existing backend tests pass; the 59 new/changed grounding tests pass; `ruff` is clean; the prompt file is byte-for-byte identical to PRD §4.1's "Full proposed text" block.

## Blocking

### 1. `_is_verbatim_quote` / `_locate_quote_offsets` do not detect a fabricated quote made of characters `normalize_text` drops entirely

**File:** `backend/care_plan/pipeline.py:109-119` (`_is_verbatim_quote`), `:151-212` (`_locate_quote_offsets`).

**What breaks:** The blank-quote guard at line 116 (`if not quote.strip(): return False`) only rejects quotes that are pure *Python whitespace*. It does not reject a quote consisting of non-whitespace Unicode characters that `normalize_text` nonetheless reduces to the empty string (NFKD decomposition + `encode("ascii", "ignore")` drops many symbols, currency signs, CJK characters, and other non-ASCII characters entirely — confirmed empirically: `©`, `§`, `×`, `÷`, `±`, `µ`, `∞`, `€`, `£`, `¥`, `★`, `☺`, `→`, `•`, `°`, `‰`, `Ω`, `π`, `中`, `文`, `の`, `Я` all normalize to `""`). Line 118's `normalize_text(quote) in normalize_text(unit_text)` then degenerates to `"" in normalize_text(unit_text)`, which is `True` for **any** `unit_text` — the exact vacuous-substring problem the docstring says the guard exists to prevent, just reached through a different door than plain whitespace.

Because the check reads `len(quote) >= 12` as one of its three informativeness passes, a quote of 12+ such symbols also clears `_is_informative_quote` (line 130), since it is a single "word" ≥ `_QUOTE_LONG_WORD_MIN_LENGTH` (7) characters long by raw `len()`, with no requirement that the word contain any actual letters.

Once both checks pass, `_locate_quote_offsets` (line 151) computes:
```python
idx = normalized_unit.find(normalized_quote)   # normalized_quote == "" -> idx == 0 always (str.find("") == 0)
char_start = spans[idx][0]                      # spans[0][0] == 0
char_end = spans[idx + len(normalized_quote) - 1][1]   # len(normalized_quote) - 1 == -1 -> spans[-1][1]
```
`spans[-1]` is Python's *last* element — not "one before the match," which doesn't exist for a zero-length match. The result is `(0, len(unit_text))`: the **entire unit's raw text**, regardless of where anything nominally "matched." If `unit_text` is `""` (an all-whitespace/empty unit, one of the task's own named edge cases), `spans` is `[]` and `spans[0]`/`spans[-1]` raise an unhandled `IndexError` instead — which `ground()` does not catch (it has no try/except of its own per §4.6), so this crashes the pipeline step rather than raising the intended `SimplifyError`.

**Concrete reproducing input and actual output**, run from `/tmp/claude-0/-root-projects-juno-projects-simplify-med/bad02ae1-feed-49a5-9be3-33707d5a7549/scratchpad/trace5.py`:

```python
unit_text = "Patient has hypertension and continues lisinopril"
quote = "±" * 12   # 12 plus-minus signs; normalize_text(quote) == ""

_is_verbatim_quote(quote, unit_text)      # -> True   (should be False: shares zero real characters)
_is_informative_quote(quote)              # -> True   (len(quote) == 12 >= _QUOTE_MIN_LENGTH)
_locate_quote_offsets(quote, unit_text)   # -> (0, 49)
unit_text[0:49]                            # -> 'Patient has hypertension and continues lisinopril'  (the WHOLE unit)
```
Actual captured output:
```
quote.strip() truthy (passes blank guard): True
normalize_text(quote): ''
_is_verbatim_quote: True
_is_informative_quote: True
locate_quote_offsets: (0, 49) of unit_text length 49
recovered raw slice: 'Patient has hypertension and continues lisinopril'
recovered slice == full unit_text? True
```
And end-to-end through `_verify_ledger`, with a `_GroundedFactRaw` whose `text` is openly fabricated:
```python
drafts = [_GroundedFactRaw(category="medications", unit_id=1, quote="±"*12,
                            text="FABRICATED: patient takes unicorn tears 500mg twice daily")]
facts = _verify_ledger(drafts, units)
```
Output:
```
Number of facts surviving: 1
Fact: id=1 category='medications' unit_id=1 char_start=0 char_end=49 text='FABRICATED: patient takes unicorn tears 500mg twice daily'
quote_for equivalent slice: 'Patient has hypertension and continues lisinopril'
```
The fabricated fact is **not dropped**. It becomes a `Fact` whose evidence pointer (what `quote_for()` will show 04/05) spans the entire cited unit, with completely invented `text`. This is precisely the scenario PRD §4.5 says must be caught "with certainty" ("Do not fabricate a fact with no unit backing it... a model that invents evidence cannot produce a real substring of the source") — here it isn't.

**Second manifestation (crash, not silent pass-through)**, same root cause, empty-unit case:
```python
_is_verbatim_quote("±"*12, "")     # -> True
_is_informative_quote("±"*12)      # -> True
_locate_quote_offsets("±"*12, "")  # -> IndexError: list index out of range
```
Actual output:
```
_is_verbatim_quote: True
_is_informative_quote: True
EXCEPTION: IndexError list index out of range
```
This exception is unhandled by `ground()` (which relies on `SimplifyError` for its documented failure modes) and would propagate as a raw `IndexError` rather than `PIPELINE_VALIDATION_FAILED`.

**Why the existing tests don't catch this:** `test_is_verbatim_quote_rejects_fabricated_quote` (`test_pipeline_grounding.py`) uses a plausible-but-wrong ASCII paraphrase (`"increase metoprolol to 50mg"`) as its fabricated quote — a real, non-empty normalized string that legitimately fails the substring check. No test exercises a quote whose *normalized* form is empty while its *raw* form is non-blank. `test_is_verbatim_quote_rejects_blank_quote` only covers `""` and `"   "`, both of which are already caught by `quote.strip()`.

**Suggested direction (not a fix I'm applying — read-only review):** guard on the normalized form, not the raw form, e.g. `if not normalize_text(quote): return False` in `_is_verbatim_quote` (this alone closes both the false-verbatim-match and the downstream `_locate_quote_offsets` div-by-zero-length issue, since `_locate_quote_offsets` is only ever called after `_is_verbatim_quote` passes); and/or add a defensive `if not normalized_quote: raise AssertionError(...)` at the top of `_locate_quote_offsets` itself so the invariant violation can never silently produce a full-unit span even if some other future caller skips the guard.

## Non-blocking

1. **Offset recovery can widen a match by one raw character when the match boundary falls inside a multi-character-expanding raw character (e.g., a compatibility ligature).** `backend/care_plan/pipeline.py:151-212`. Traced concretely: `unit_text = "AﬁB"` (`ﬁ` = U+FB03-style single-codepoint ligature that NFKD-decomposes to `"fi"`) normalizes to `"afib"` with `spans = [(0,1),(1,2),(1,2),(2,3)]` (both `f` and `i` map to the same raw span `(1,2)`, since they come from one raw character). Quoting `"ib"` (a real normalized substring, starting mid-ligature) recovers `(1, 3)` → raw slice `"ﬁB"`, and `normalize_text("ﬁB") == "fib" != normalize_text("ib") == "ib"` — the recovered raw span, re-normalized, no longer equals the quote's normalized form; it has one extra leading character. Quoting `"af"` similarly recovers `"Aﬁ"` (`normalize_text` → `"afi"`, not `"af"`). This is a structural limitation (a Python string index cannot land "inside" a single codepoint), not an implementation slip, and the blast radius is bounded to widening the recovered span by at most one raw character on one or both ends — it never points at the wrong unit or a materially different location, and a real LLM's quote is very unlikely to intentionally begin/end exactly inside a ligature's decomposition (ligature-bearing PDF extractions are real, but LLM-generated quotes tend to align to word/phrase boundaries). Still, it means the invariant the test suite asserts in spirit (`test_verify_ledger_populates_char_start_and_char_end_from_quote`'s "module-tolerant" recovery) can fail for this input, and no test exercises a ligature at all despite `normalize_with_offsets`'s own docstring calling ligatures out by name as a case it's designed to handle. Worth a one-line caveat in the docstring and/or a regression test, but not worth blocking on given the narrow, hard-to-trigger window.

2. **`normalize_with_offsets`/`normalize_text` are 36×–67× slower than the pre-existing implementation for large documents**, due to the new per-character `unicodedata.normalize` + `encode`/`decode` loop replacing a single whole-string call. Measured on this machine (`scratchpad/perf.py`, `perf2.py`):

   | input size | old `normalize_text` | new `normalize_text` | ratio |
   |---|---|---|---|
   | 1,000 chars | 0.022 ms | 0.804 ms | 36× |
   | 20,000 chars | 0.276 ms | 12.3 ms | 45× |
   | 100,000 chars | 1.4 ms | 63.9 ms | 45× |
   | 500,000 chars (= `Constants.CarePlan.MAX_TEXT_LENGTH`, the documented input ceiling) | 5.2 ms | 347.8 ms | 67× |

   `utils/term_detection.py:detect_terms` calls `normalize_text` once on the *entire* input document, and `build_glossary_from_simplified_text` calls it once on the entire simplified output — both realistic full-document-length calls, not per-term. At the documented worst-case document size this adds roughly +340 ms per call (~0.7 s across both call sites) to a pipeline whose other steps are multi-second LLM calls, so it's very unlikely to be user-visible, but it's a genuine, measured regression worth knowing about if latency or Cloud Run CPU cost is ever budgeted tightly. `jargon_db.py`'s per-alias calls (short strings, `lru_cache`d lookup tables built once per process) are not a practical concern.

3. **Import placement**: `from models.base import JsonModel` (`backend/care_plan/pipeline.py`, added just after the pre-existing `WrapStepFn = Callable[...]` line) sits between an executable statement and the rest of the import block rather than with the other new imports listed in PRD §4.2 ("added to the existing import block"). This mirrors a pre-existing oddity in the file (the import block was already split around `WrapStepFn` before this diff) rather than introducing a new one, and has no behavioral effect — purely cosmetic.

## Suggestions

- Add a test case to `test_pipeline_grounding.py` covering a quote that is non-blank but normalizes to the empty string (e.g. a run of symbol/CJK characters), asserting `_is_verbatim_quote` returns `False` — this is the exact gap that let Blocking Finding 1 through, and the PRD's own task language ("the fabricated-quote case explicitly called out in the task") suggests this class of input was meant to be covered.
- Add a defensive assertion in `_locate_quote_offsets` that `normalized_quote` is non-empty before calling `.find()`, independent of fixing the upstream guard — cheap insurance against the same bug class re-appearing if another call site is ever added.
- Consider noting the ligature-boundary limitation (Non-blocking #1) in `_locate_quote_offsets`'s docstring, since the docstring already discusses two other edge cases (multiple occurrences, whitespace spanning) at similar length and this one is currently unaddressed there.
- If per-request latency or CPU cost on large documents is ever measured to matter, `normalize_with_offsets` could avoid the per-character `unicodedata.normalize` call (the dominant cost) by decomposing the whole string once with `unicodedata.normalize("NFKD", text)` while separately tracking, per *output* character, which original character produced it via `unicodedata.decomposition`/length bookkeeping — but this is speculative optimization, not something the measured numbers currently justify.

- **`_locate_quote_offsets` correctness for the same hard cases**, checking `unit_text[char_start:char_end]` reproduces the intended raw span (not just that `normalize_text` agrees): a raw double-space collapsing to the quote's single space (recovered slice included the full raw double space, e.g. `"cont.  metoprolol 25mg"`); a raw tab similarly; a case difference (recovered slice preserved the unit's original casing, `"METOPROLOL 25mg"`); a repeated quote (offsets pointed at the first occurrence); a quote beginning right after a leading whitespace run (`"   Pt to cont..."` → correctly excluded the leading spaces); a quote ending right before a trailing whitespace run (correctly excluded trailing spaces); a quote starting/ending immediately adjacent to an *interior* collapsed double-space run on both sides (both correctly resolved to the raw boundary, not the normalized one); a dropped non-ASCII character strictly inside the matched span (`"Temp 98.6°F now"`, quote `"98.6F now"` → recovered raw slice `"98.6°F now"`, degree sign included by contiguity, `normalize_text` of the slice equals `normalize_text` of the quote).
