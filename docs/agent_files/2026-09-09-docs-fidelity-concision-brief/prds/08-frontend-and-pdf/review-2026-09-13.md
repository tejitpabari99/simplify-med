## Verdict: **Changes required**

One material content-loss bug (Medication.change silently dropped from all patient-facing surfaces) should be fixed before this is considered done — it defeats a piece of the backend contract this PRD was supposed to mirror, and the PRD's own text is internally contradictory about it rather than deciding to drop it on purpose. Everything else — the eight-card collapse, `nextSteps.ts`'s shared ordering module, null-safe urgency handling, the PDF activation, `hideLowPriority` removal, HTML escaping — is implemented faithfully and is well tested.

## Security review (no XSS/injection issues found)

Checked every user/LLM-controlled string interpolated into `buildPdfHtml.ts`'s HTML template: `summary`, `reason_for_visit[].reason/description`, `diagnosis.details[].*`, every Next Steps row field (`title`/`why`/`detail`/`steps[]`), `warning_signs[].*`, `questions[]`, `low_priority[]`, and glossary `term`/`definition` — all pass through `escapeHtml()` before interpolation; none found un-escaped. `downloadReport.ts` also nulls `printWindow.opener` after `window.open`, a defense-in-depth measure against the injected-markup-reaching-back-into-the-opener-tab class of issue (already present, already tested at `downloadReport.test.ts:43-51`). No prompt-injection surface in this PRD (no LLM calls). No PII logging concern (no `console.*`/logging calls touch care-plan content in the files reviewed).
